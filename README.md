# الرعاية العاجلة — منصة التسجيل الذاتي للمراجعين

منصة عربية (RTL) لتسجيل المراجعين ذاتياً في أقسام الرعاية العاجلة، مبنية على واجهة ثابتة
عالية الأداء + **Supabase** لتخزين الملفات والملاحظات + خادم Node.js (Express) للمزامنة
مع **رقيم** و**صحتي**.

البيانات لم تعد تُحفظ في المتصفح: كل ملف يُحفظ في Supabase، والملاحظات تُشفَّر في
المتصفح (`AES-256-GCM`) قبل رفعها. الواجهة تحتوي المفتاح **العام** فقط (anon/publishable)،
ولا تحتوي أي محاكاة ولا أي مفتاح سري؛ RLS في قاعدة البيانات يضمن عزل كل مريض عن غيره.

## 1) المكوّنات

| المكوّن | المسار | الوصف |
| --- | --- | --- |
| الواجهة | `index.html` · `assets/` | HTML/CSS/JS + Supabase JS CDN |
| قاعدة البيانات السحابية | `supabase/schema.sql` | الجداول + RLS + الفهارس |
| طبقة السحابة | `assets/js/cloud.js` | دخول/جلب/إضافة/تعديل/حذف الملاحظات |
| الخادم | `server/src/` | Express 5 + `node:sqlite` (مدمج في Node ≥ 22.5) |
| محاكي الأنظمة | `server/src/adapters/mockAdapter.js` | يعيش داخل الخادم فقط |
| الاختبارات | `server/test/api.test.js` | 36 اختباراً لمسارات الـ API |
| تطبيق سابق محفوظ | `vault/` | تطبيق «ملفاتي» السابق، محفوظ كما هو |

### الصفحات

- `#/` الصفحة التعريفية.
- كشك التسجيل الذاتي: الفئة → الوثيقة → البيانات → رقم الانتظار.
- بوابة المريض: الملف، الزيارات، الملاحظات الخاصة، تصدير نسخة من الملف.
- تبديل عربي/إنجليزي مع قلب كامل للاتجاه (RTL ↔ LTR).

## 2) تشغيل الخادم

```bash
cd server
npm install
npm start
```

يعمل افتراضياً على `http://localhost:3000` وقاعدة البيانات في `server/data/clinic.db`
(تُنشأ تلقائياً، ومستثناة من Git).

### متغيّرات البيئة

| المتغيّر | الافتراضي | الوظيفة |
| --- | --- | --- |
| `PORT` | `3000` | منفذ الخادم |
| `HOST` | `0.0.0.0` | عنوان الاستماع |
| `DB_PATH` | `server/data/clinic.db` | مسار قاعدة SQLite |
| `PIN_ITERATIONS` | `120000` | دورات PBKDF2 لتشتيق رمز الدخول |
| `CORS_ORIGIN` | `*` | أصل الواجهة المسموح |
| `MOCK_FAIL_RATE` | `0.15` | نسبة فشل محاكي رقيم/صحتي |
| `MOCK_MIN_DELAY` / `MOCK_MAX_DELAY` | `400` / `1100` | زمن استجابة المحاكي (مللي ثانية) |
| `SYNC_BACKOFF_MS` | `300` | أساس التباعد بين محاولات المزامنة (3 محاولات) |

### تشغيل الواجهة محلياً

```bash
# من جذر المستودع — أي خادم ملفات ثابتة يعمل
npx serve .
# أو
node _serve.js     # خادم تطوير بسيط على المنفذ 8379
```

تكتشف الواجهة الخادم تلقائياً بالترتيب: `window.ENAYA_API` ←
`http://localhost:3311` ← `http://localhost:3000` ← نفس الأصل (`/health`).
وإن لم تجد خادماً فإنها تعمل في **وضع محلي**: تحفظ الملف مشفّراً على الجهاز
وتُظهر تنبيهاً صريحاً بأن المزامنة غير متاحة.

## 3) واجهة البرمجة (API)

المسارات متاحة على الجذر وعلى `/api` معاً.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/health` | فحص الجاهزية والأنظمة الموصولة |
| `POST` | `/patients` | تسجيل مراجع جديد أو دخول صاحب وثيقة مسجّلة |
| `GET` | `/patients/:docType/:docNo` | ملف المراجع وزياراته (يتطلب جلسة) |
| `POST` | `/visits` | إنشاء زيارة + رقم انتظار + مزامنة (يتطلب جلسة) |
| `POST` | `/patients/:docType/:docNo/session` | استئناف الجلسة على جهاز جديد برمز الدخول |

`docType` أحد: `nid` (هوية) · `iqama` (إقامة) · `passport` (جواز).

### مثال: تسجيل

```http
POST /patients
Content-Type: application/json

{
  "documentType": "nid",
  "documentNumber": "1010101010",
  "category": "citizen",
  "birthDate": "1990-01-01",
  "phone": "0551234567",
  "pin": "Demo1234",
  "consent": true
}
```

`201 Created` عند الإنشاء، و`200 OK` عند إعادة تسجيل وثيقة موجودة برمز الدخول الصحيح.
كلاهما يعيد `{ created, token, patient, visits }`.

بدلاً من `birthDate` الميلادي يمكن إرسال `birthDateHijri: { year, month, day }`
ويحوّله الخادم بتقويم **أم القرى**.

### مثال: زيارة

```http
POST /visits
Authorization: Bearer <64-hex token>
Content-Type: application/json

{ "patientId": "PT-…", "reason": "استشارة" }
```

يعيد `{ visit: { queueNumber, status, … }, sync: { raqeem, sehhaty } }`
حيث `sync.*.status` أحد `ok` أو `fail` (مع `detail` عند الفشل).

### الأخطاء

```json
{ "error": { "code": "VALIDATION_FAILED", "fields": { "documentNumber": "eNid" } } }
```

- `422` خطأ تحقق، والقيم في `fields` هي مفاتيح ترجمة تعرضها الواجهة.
- `401` جلسة مطلوبة/غير صالحة أو رمز دخول خاطئ (`INVALID_PIN`).
- `403` محاولة الوصول إلى ملف مراجع آخر.
- `404` مراجع غير موجود · `400` نوع وثيقة غير صالح أو JSON تالف.

## 4) نموذج الأمان والخصوصية

- **رمز الدخول (PIN)** لا يُحفظ نصاً في خادم المنصة: يُشتق بـ `PBKDF2-SHA256` (180,000 دورة) مع ملح عشوائي. في Supabase Auth يُستخدم كلمة مرور للحساب (مُجزّأة هناك)، ولا يُخزَّن في أي جدول.
- **رمز الجلسة** 32 بايت عشوائية، يُحفظ في القاعدة مجزّأً بـ `SHA-256`، ويُرسل في
  ترويسة `Authorization`. كل تسجيل/دخول يدوّر الرمز.
- **العزل بين المراجعين**: كل قراءة أو زيارة تتحقق من أن الجلسة تخص نفس صاحب الوثيقة،
  وإلا تُرجع `403`.
- **الملف السحابي**: يُحفظ في Supabase (جداول `patients` و`visits` و`notes`) ولا يوجد
  أي تخزين لبيانات المرضى في `localStorage`. حساب المريض في Supabase Auth يُعرَّف ببريد
  اصطناعي مشتق من بصمة `SHA-256` لرقم الوثيقة؛ لا يُخزَّن رقم الوثيقة نفسه.
- **التشفير من طرف العميل**: نص الملاحظة (العنوان والنص) يُشفَّر بـ `AES-256-GCM` قبل
  الإرسال، والمفتاح يُشتق من رمز الدخول + ملح خاص بالمريض. حتى مسؤول قاعدة البيانات
  يرى حمولة مشفّرة فقط.
- **RLS**: كل صف في الجداول الثلاثة مربوط بـ `user_id = auth.uid()`، فلا يستطيع أي
  مستخدم قراءة أو تعديل صفوف غيره حتى لو حصل على المفتاح العام.
- **التصدير** لا يتضمن أي رمز جلسة أو مفتاح.
- الواجهة خالية من أي كلمة مرور أو مفتاح سري أو محاكاة؛ المحاكي كله داخل الخادم.
  المفتاح الوحيد الموجود في الواجهة هو المفتاح **العام** (anon/publishable)، وهو آمن
  للنشر بشرط تفعيل RLS.

> ملاحظة: هذه نسخة تجريبية. لا تُدخل بيانات صحية حقيقية.

### ربط Supabase — خطوات التنفيذ

1. أنشئ مشروعاً جديداً على [supabase.com](https://supabase.com).
2. افتح **SQL Editor → New query**، والصق محتوى الملف
   [`supabase/schema.sql`](supabase/schema.sql) كاملاً، ثم اضغط **Run**.
3. من **Authentication → Sign In / Providers → Email**:
   - عطّل **Confirm email** (وإلا لن يستطيع المريض الدخول بعد التسجيل).
   - اترك **Enable Sign-ups** مفعّلاً.
4. من **Project Settings → API** انسخ:
   - **Project URL** → `url`
   - **anon public** أو **publishable** key → `anonKey`
5. ضع القيمتين في `assets/js/supabase-config.js` ثم أعد نشر الواجهة.

```js
window.URGENT_CARE_SUPABASE = {
  url: 'https://YOUR-PROJECT.supabase.co',
  anonKey: 'eyJ...', // المفتاح العام فقط — ليس service_role
  emailDomain: 'patients.urgentcare.app',
};
```

> ⚠️ **لا تضع `service_role` أو أي مفتاح سري في الواجهة.** أي قيمة هناك تُنزَّل إلى
> المتصفح وتُعدّ علنية. الملفات المحلية التي قد تحتوي أسراراً
> (`supabase-config.local.js`, `.env`, `secrets/`) مستثناة في `.gitignore`.

إذا لم تُضف المفاتيح بعد، يعمل التطبيق في **وضع تجريبي داخل الذاكرة فقط** (لا يحفظ
شيئاً بعد إغلاق الصفحة) ويظهر شعار «وضع تجريبي» في الشريط العلوي.

### تغيير رمز الدخول (داخل البوابة)

من تبويب **ملفي** ← زر **تغيير رمز الدخول**. العملية تجري في هذا الترتيب:

1. يتحقق Supabase من الرمز الحالي (إعادة تسجيل دخول).
2. تُفكّ تشفير كل الملاحظات بالمفتاح القديم في الذاكرة.
3. تُشفَّر مسبقاً بالمفتاح الجديد — قبل أي كتابة.
4. تُحدّث كلمة مرور الحساب في Supabase Auth.
5. تُكتب الحمولات الجديدة؛ وأي فشل في هذه المرحلة يعيد الملاحظات وكلمة المرور
   إلى حالتهما السابقة.

الملح (`salt`) يبقى كما هو، لذلك لا تعتمد أي ملاحظة على صف `patients` بعد الكتابة.
إذا نُسي الرمز الجديد فلا يمكن استعادته — الحل الوحيد حذف الحساب من Supabase ثم
التسجيل من جديد (كما في صفحة «نسيت رمز الدخول؟»).

### لوحة الموظفين

1. شغّل ملف [`supabase/staff.sql`](supabase/staff.sql) مرة واحدة في **SQL Editor**.
2. أنشئ حساب الموظف من صفحة **التسجيل الذاتي** (وثيقته ورمزه)، ثم سجّل الخروج.
3. امنحه صلاحية الموظف من SQL Editor بعد استبدال الرقم والاسم:

```sql
insert into public.staff (user_id, full_name, role)
select u.id, 'موظف الاستقبال', 'staff'
from auth.users u
where u.email = public.doc_email('nid', '1012345678')
on conflict (user_id) do update set full_name = excluded.full_name;
```

4. من صفحة **بوابة المريض** اضغط **دخول الموظفين** أسفل البطاقة، ثم أدخل وثيقة
   الموظف ورمزه.

ما تستطيعه اللوحة:

- **تبويب الزيارات**: عرض كل الزيارات، البحث برقم الانتظار/الوثيقة/الجوال،
  وتغيير حالة الزيارة (نداء، إتمام، إرجاع للانتظار، إلغاء).
- **تبويب المرضى**: عرض **كل من أنشأ حساباً** حتى لو لم يطلب زيارة، مع الرقم
  المقنّع والجوال والفئة وتاريخ التسجيل وعدد الزيارات لكل مريض.
- تحديث القائمة بزر «تحديث» (يقرأ الزيارات والمرضى معاً).

> الحد الحالي: تُعرض حتى 1000 حالة مسجّلة (حد PostgREST الافتراضي) وأحدث 300
> زيارة. مركز يتجاوز هذا العدد يحتاج ترقيماً (pagination) لاحقاً.

لعرض قائمة المسجّلين من SQL Editor مباشرةً (خارج اللوحة):

```sql
select p.masked_doc, p.phone, p.category, p.created_at,
       (select count(*) from public.visits v where v.user_id = p.user_id) as visits
from public.patients p
order by p.created_at desc;
```

> عرض `staff_patients` لا يعمل داخل SQL Editor لأنه يعتمد على `auth.uid()`،
> لذا استخدم الجدول `patients` عند الاستعلام الإداري.

ما لا تستطيعه (بالتصميم): قراءة ملاحظات المرضى. لا توجد أي سياسة RLS تمنح
الموظف وصولاً إلى جدول `notes`، والملاحظات مشفّرة بمفتاح رمز المريض أصلاً.
كما أن قراءة بيانات المراجع تمر عبر عرض `staff_patients` الذي لا يكشف بصمة
الوثيقة (`doc_fingerprint`) ولا ملح التشفير (`salt`).

لسحب الصلاحية دون حذف الحساب:

```sql
delete from public.staff where user_id = (
  select id from auth.users where email = public.doc_email('nid', '1012345678')
);
```

## 6) النشر

الواجهة ثابتة بالكامل، لذا تُنشر على **GitHub Pages** من الفرع `main` (المجلد الجذر).
خادم الـ API لا يعمل على Pages؛ عند فتح الموقع المنشور:

- **البيانات والملاحظات** تُحفظ مباشرة في Supabase (لا تحتاج خادماً).
- **المزامنة مع رقيم وصحتي** تحتاج تشغيل خادم الـ API، ويُشار إليه عبر:

```html
<script>window.ENAYA_API = 'https://api.example.com';</script>
```

أو بتشغيل الخادم على نفس أصل الواجهة. بدون خادم يظهر رقم انتظار محلي وحالة
«غير متاح» للمزامنة، مع بقاء البيانات محفوظة سحابياً.
